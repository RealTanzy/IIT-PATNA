A minimal 2-day LoRA/QLoRA experiment plan
Prepared for your current CoT vs A* reasoning setup
Scope: one dataset, one base model, rescue-rationale rewriting, LoRA fine-tuning, and a clean 
evaluation in 48 hours.
Goal
Show that some CoT failures can be repaired 
by distilling successful A* traces into short 
linear rationales.
Recommended minimal scope
Use one dataset first (StrategyQA 
recommended), one already-working base 
model, and only the A*-rescued subset plus a 
preservation subset.
Training method LoRA by default; QLoRA if VRAM is tight. Use 
TRL SFTTrainer with PEFT adapters.
Main success metric
Rescue rate on the old “CoT wrong / A* right” 
dev examples, while preserving performance 
on old “CoT right / A* wrong” cases.
Why this exact experiment
Your paper already shows the decisive signal: CoT and A* are complementary, the oracle gap is 
large, and the strongest problem categories are non-linear evidence aggregation, hypothesis 
elimination, and multi-hop chaining. The smallest publishable next step is to test whether 
successful A* traces can be rewritten into compact linear rationales and then distilled back into a 
CoT-style decoder.
 Do not try to solve everything in 2 days. Do not add mechanistic interpretability yet.
 Do not start with all datasets or all models. One dataset + one base model is enough for the first 
result.
 Do not distill raw A* traces directly. Rewrite them first into short linear rationales.
Anchoring assumptions from your current paper
 Oracle gains are already large: +9.79 on StrategyQA, +13.51 on LogicQA, and +14.10 on 
HotpotQA over the stronger single method.
 The A*-only bucket is large enough to matter: 10.8% on StrategyQA, 13.5% on LogicQA, and 
17.4% on HotpotQA.
 A* helps most on non-linear evidence aggregation, hypothesis elimination, and multi-hop 
chaining; CoT remains stronger on direct factual reasoning and globally coherent 
argumentation.

1. Exact scope for the 48-hour run
Recommended scope
1. Dataset: StrategyQA first. It is the easiest minimal setting because answers are boolean, 
rationales can be short, and evaluation is cheap and robust.
2. Model: use the same model family that already produced your CoT/A* results if it is already 
integrated into your codebase. If you have A100-class hardware, use the model you already 
evaluated. If VRAM is tight, switch to QLoRA on the same or a slightly smaller instruction-
tuned base model.
3. Train only one adapter. Do not train multiple variants on day 1.
4. Create only one training set version first: “preserve + rescue.”
5. Evaluate on one held-out dev split with four buckets: both-correct, CoT-only, A*-only, both-
wrong.
Why StrategyQA first
 Short outputs reduce noise in rationale rewriting and training.
 Boolean evaluation lets you move fast and detect regressions immediately.
 Your paper already shows a meaningful A*-only bucket and a strong oracle gap there, so 
rescue distillation is testable.
Fallback choice
If your existing pipeline for StrategyQA is messy but HotpotQA is already clean, use HotpotQA 
instead. The only thing that matters for this 2-day run is implementation speed, not theoretical 
purity.

Why not train only on rescue?
Because the adapter will over-specialize to the failure regime and can degrade ordinary CoT 
behavior. For the first run, preserving baseline competence matters almost as much as rescue.
4. Generate compact rescue rationales from successful A* traces
This is the central step. The target is not the raw A* trace. The target is a short, direct, coherent 
linear rationale that preserves the decisive logic found by A* but removes search artifacts.
Input fields for each rescue example
 question
 gold answer
 raw CoT trace and answer (optional but useful for debugging)
 successful A* trace and answer

Rewriting prompt template
You are given a question, the correct answer, and a successful search-style reasoning trace.
Rewrite the trace into a compact linear chain-of-thought that a single-pass reasoner could plausibly produce.
Rules:
1. Keep only logically necessary steps.
2. Remove explicit branching, search artifacts, retries, and repeated steps.
3. Do not add unsupported facts.
4. Use at most 4 numbered steps.
5. End with: Therefore, the answer is: <answer>.
Question: {question}
Correct answer: {gold}
Successful A* trace: {astar_trace}
Output only the rewritten rationale.
What makes a rewrite acceptable
 It is shorter than the source A* trace.
 It preserves the decisive bridge fact, elimination logic, or multi-hop link that made A* succeed.
 It reads like one smooth trajectory rather than a tree search log.
 Its final answer matches the gold answer exactly.
Fast verification pass
Given the question and the rewritten rationale, answer two things:
(1) Does the rationale support the stated answer? [YES/NO]
(2) Is the rationale introducing unsupported new claims not present in the successful search trace? [YES/NO]
Keep the example only if (1)=YES and (2)=NO.
Hard filters for the 2-day run
 Maximum rationale length: 120–160 tokens.
 Maximum steps: 4.
 Reject if the rewriter says “another possibility”, “branch”, “option 1”, or similar search 
language unless it is a multiple-choice elimination example.
 Reject if the answer extracted from the rewritten rationale does not match gold.
 Reject if the rationale is nearly identical to the original wrong CoT trace.

5. Convert the data into LoRA training format
Recommended format: conversational prompt-completion
Use a chat-style structure so you can train only on the assistant output. TRL supports 
conversational data and can compute loss only on assistant messages with 
assistant_only_loss=True, provided the chat template exposes assistant token masks. If your 
template does not support that cleanly, then use a prompt-completion format and compute 
completion-only loss instead.
Simple conversational record
{
  "messages": [
    {"role": "system", "content": "You are a careful reasoner. Produce a short chain of thought and then the final 
answer."},
    {"role": "user", "content": "Question: ..."},
    {"role": "assistant", "content": "1. ...\n2. ...\nTherefore, the answer is: yes."}
  ]
}
Preserve examples should use the same format
For preserve examples, the assistant content should be the original good CoT if it is already 
compact and decent. If the baseline CoT is too long or messy, rewrite it lightly into the same short 
format so that train targets are stylistically consistent.
6. LoRA/QLoRA training recipe for the 2-day experiment
Choice of method
 Use plain LoRA if the model already fits comfortably in BF16/FP16 on your GPU.
 Use QLoRA if VRAM is tight or if you want the safest minimal run on a single GPU. PEFT 
documents the standard pattern: load the base model in 4-bit via BitsAndBytesConfig, call 
prepare_model_for_kbit_training(), and then attach a LoraConfig adapter on top. NF4 and 
double quantization are the standard 4-bit choices in the official guide.

Minimal training skeleton (TRL + PEFT)
import torch
from datasets import load_dataset
from transformers import AutoTokenizer, AutoModelForCausalLM, BitsAndBytesConfig
from peft import LoraConfig, prepare_model_for_kbit_training
from trl import SFTTrainer, SFTConfig
BASE_MODEL = "your-base-model"
USE_4BIT = True
quant_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_use_double_quant=True,
    bnb_4bit_compute_dtype=torch.bfloat16,
) if USE_4BIT else None
tokenizer = AutoTokenizer.from_pretrained(BASE_MODEL, use_fast=True)
model = AutoModelForCausalLM.from_pretrained(
    BASE_MODEL,
    quantization_config=quant_config,
    torch_dtype=torch.bfloat16 if not USE_4BIT else None,
    device_map="auto",
)
if USE_4BIT:
    model = prepare_model_for_kbit_training(model)
peft_config = LoraConfig(
    r=16,
    lora_alpha=16,
    lora_dropout=0.05,
    bias="none",
    task_type="CAUSAL_LM",
    target_modules="all-linear",
)
train_args = SFTConfig(
    output_dir="outputs/adapters/rescue_lora",
    learning_rate=1e-4,

  --in_jsonl data/rescue_pairs/rewritten_rescues.jsonl \

  --manifest data/rescue_pairs/rescue_manifest.csv \

  --train_out data/lora_train/train.jsonl \
  --dev_out data/lora_train/dev.jsonl

  --dev_file data/lora_train/dev_eval_questions.jsonl \
